# Проверка именованных исходов

Оцениваем полные отчёты действующего сайта. Загружаем только ТЗ. Сравниваем вычисленные интерпретатором надписи с эталоном. Порядок сторон может зависеть от порядка цитат, поэтому проверяем связь исхода с исходным правилом.

| ТЗ | Спорный вход | Исход по правилу | Исход по приёмке | Согласованный контроль |
|---|---|---|---|---|
| [Переплётная мастерская](../hosted-reserve/bindery-site.md) | 18 мм | Швейный участок | Клеевой участок | 17 мм → Клеевой участок у обеих сторон |
| [Табло читального зала](light-meter.md) | 40 лк | День | Сумерки | 55 лк → День у обеих сторон |

У табло контроль задан выше границы, приёмка записана обычным текстом. У мастерской контроль ниже границы, приёмка дана в таблице. Приёмочные строки задают конкретные входы. На неопределённых входах вывод приёмки нельзя выдавать за подтверждённое требование.

Для успеха нужен фактический Cloudflare в паспорте, статус `executed`, совпадение скачанного исходного хеша, обе дословные ссылки и воспроизводимый автономный расчёт. Дополнительно проверяем, что подмена одного результата ломает проверку.

Во всех четырёх паспортах записаны фактический провайдер Cloudflare Workers AI, модель `@cf/openai/gpt-oss-120b` и переход после HTTP 429 от Gemini. Время взято из `run.elapsed_seconds` каждого отчёта. Это отдельные наблюдения. Среднее время и воспроизводимость новых генераций по ним не измерены.

В новых отчётах модель извлекла сравнение и две строки приёмки. Вторым вызовом та же модель прочитала исходник на обоих входах, без доступа к программе и её результатам. Сервис записал `executed` после совпадения всех четырёх чтений с вычислениями. Сверка ниже воспроизводит расчёты, проверяет ссылки, хеши исходников, область входов и отказ при подмене показания. Для неё достаточно Python.

```sh
python3 -m eval.route-decisions.verify
```
