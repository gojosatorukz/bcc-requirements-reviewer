# Архитектура и критерии готовности

Предложение к разработке, 26.11.2026. Рабочее название — «Разбор ТЗ». Назначение — выявить несовместимые решения в спецификации до передачи в разработку и провести аналитика от замечания к проверяемой приёмке. Исходный материал и официальный отчёт должны сохраняться раздельно. [Задание организаторов](https://github.com/BCC-HUB/ai-requirements-validator-task/blob/928c1aa364265426105b69ba7a3444eac11b22db/README.md)

## Почему выбрана такая архитектура

Простой запрос ко всей спецификации — обязательный соперник при оценке. Он может оказаться лучше сложного варианта на некоторых документах. Несколько агентов, голосующих по одному ответу, могут воспроизвести одну ошибку. Семантический поиск близких фраз тоже имеет слабое место — текст о месяце и строка приёмки с датами выглядят по-разному. Предлагаемый вариант совмещает полный обзор небольшого документа, проверку локальных правил и исполнимые контрпримеры там, где язык правил способен выразить задачу. Каждый дополнительный шаг оправдывается отдельным замером.

## Данные от источника до решения

1. **Источник.** Хеш входного файла, заголовки и нумерация, строки Markdown либо страницы PDF. Для каждой ячейки хранить путь до заголовков таблицы, для примера ответа — заголовок статуса. Для PDF проверять порядок чтения и связь ячеек. При неуверенной реконструкции помечать участок для сверки. Для скана предусмотреть OCR с координатами и пометкой качества или явно сообщить о частичной обработке.
2. **Реестр.** Одно утверждение содержит субъект, действие, условие, область действия, ожидаемое следствие, исходный ID и точный фрагмент. Сложный пункт можно разделить с сохранением общего родителя. У каждого блока исходника есть назначение — правило, пример, ограничение, контекст, шаблон или участок с неясным разбором. Такие данные нужны, чтобы заметить пропущенную таблицу.
3. **Проверка пункта.** Оценить однозначность, проверяемость, атомарность, полноту границ, ясность субъекта и результата. Разделить неопределённость требования и нехватку знаний у модели. Пояснить, когда предписанная реализация конфликтует с целью или преждевременно ограничивает решение. Ссылки на предложенные организаторами стандарты приводить вместе с конкретной проверкой. Заявление о сертификации потребовало бы иных оснований.
4. **Проверка набора.** Связать правила с примерами, API, данными и бизнес-целью. Хранить тип связи и доказательство. На малом документе дать модели полный контекст и отдельно сверить пары по общим событиям и сущностям. На большом — использовать тематический поиск вместе с явными ссылками и обзором разделов. Показывать реальное покрытие сравнений. Начать с обычных записей и связей в SQLite. Отдельная графовая база оправдана лишь при измеримом узком месте.
5. **Контрпример.** Модель предлагает две трактовки и минимальное различающее состояние. Проверяющий модуль умеет сравнить даты, диапазоны, суммы в целых минимальных единицах, счётчики, простые переходы состояний и табличные контракты. Для операций с историей воспроизводит последовательность событий. Интерпретатор обрабатывает только разрешённые декларативные операции. Результат хранит исходные допущения, входы и оба вычисленных выхода. Проверка вычислений устанавливает расхождение **при данных трактовках**. Соответствие трактовок исходному тексту проверяется отдельно. Контрпример для unsupported-правила остаётся текстовой гипотезой.
6. **Проверка и приоритет.** Для конфликта нужны пересечение условий, одна сущность и исключающие друг друга результаты. Для пробела нужны место, создающее обязательство, область поиска и недостающий факт. Сохранить отдельно факт, вывод и вопрос. Объединять дубликаты по одному решению владельца. Критичность определяется тем, блокирует ли разночтение наблюдаемое поведение или приёмку. У замечания к оформлению другой вес.
7. **Решение человека.** У вопроса есть ответственный, конкретный сценарий, варианты исхода, поле для своего ответа и возможность отложить. Предпросмотр показывает связанные правила, предполагаемую правку и будущий тест. Ответ человека сохраняется с версией. Статус «исправление подтверждено» появляется после повторного анализа исправленной копии. При изменении источника старое решение требует сверки.
8. **Результат.** CLI принимает пути входного и выходного файлов, работает без интерфейса. Офлайн-отчёт на русском и интерфейс используют одну структуру. Паспорт содержит название, дату, модель, версию агента, хеш документа и статус полноты. Далее идут реестр соответствий, анализ каждого пункта, выводы по набору, число требований и уникальных нарушений, критичные дефекты, готовность к разработке и тестированию и порядок исправлений.

Минимальный обмен между компонентами:

| Сущность | Обязательное содержание |
|---|---|
| SourceSpan | Версия документа, блок, часть и заголовок, адрес строки/страницы, оригинальный текст. |
| Requirement | Внутренний ID, исходный ID при наличии, краткая формулировка, список SourceSpan, роль блока, статус проверки. |
| Finding | Тип, ID затронутых требований, доказательства, сценарий, приоритет, вопрос, владелец, статус проверки. |
| Witness | Трактовки, основания, предусловия, события, выходы, способ проверки и ограничения. |
| Decision | Кто и что выбрал, основание, версия документа, предложенное изменение, связанные проверки. |
| Run | Версия кода, конфигурация и модель, входной хеш, статус этапов, время, токены при наличии, файл отчёта. |

### Протокол сбоев и воспроизводимости

Ошибка парсера, тайм-аут провайдера или некорректная структура ответа помечают соответствующий этап и сохраняют покрытые пункты. Статус «готово к разработке» допустим только при достаточном покрытии. Повтор ограничен, кэш привязан к хешу входа, версии промпта, схеме и модели. Офлайн-просмотр сохранённого прогона и новый запуск имеют отдельные действия. При неудачном новом запуске нельзя незаметно подставлять старый отчёт. Генерация текста модели и арифметика проходят через отдельные интерфейсы.

## Как доказываем качество

| Испытание | Метод | Внутренняя цель перед сдачей |
|---|---|---|
| Полнота приёма | Сверить реестр с вручную просмотренными разделами, таблицами и примерами. Сопоставить одинаковое содержание в Markdown и текстовом PDF. | Каждый блок учтён или явно помечен как непрочитанный. При смене формата ключевые бизнес-выводы сохраняются, ссылки открывают правильное место. |
| Истинность находок | Заранее разметить класс, источник, наблюдаемый эффект и допустимые трактовки. Рецензент проверяет смысл и цитату. Дубликаты объединяются, спорные классы выносятся в отдельную колонку. | Все показанные жюри критические находки имеют проверенные основания. Для всех выходов публикуем TP, FP, FN и знаменатели. |
| Перенос | Официальный кейс служит открытым примером. До финального прогона отложить другие мини-ТЗ, например комиссию перевода, период начисления процентов, лимит подписки. Включить чистые версии, перефразирование, новые ID и перестановку разделов. | Скрытые тексты и эталоны не попадают в промпты или правила. Для каждого документа сохранить отдельный результат. |
| Чувствительность | В копии исходника исправить D1, оставить D2. Отдельно восстановить ошибку, поменять числа и переименовать разделы. | Исправленная находка исчезает, независимая сохраняется. Появление новой корректной эквивалентной формулировки сопоставляет рецензент. |
| Чистый контроль | Выдать согласованные интервалы, явно описанный приоритет правил и разные сущности с похожими именами. Смоделировать сбой одного этапа. | Ноль ложных блокеров на заранее согласованных чистых примерах. При сбое агент выдаёт «проверка неполная». |
| Сравнение архитектуры | Три варианта на том же наборе: один сильный запрос со всем ТЗ, извлечение + сопоставление, полный вариант с контрпримером. Одинаковые модель, исходник и требования к выходу. По 3 новых прогона при доступной квоте. | Публикуем точность, полноту, разброс по прогонам, длительность и расход токенов. Отдельно сравниваем при сопоставимом лимите затрат. В защиту попадает подтверждённый выигрыш с раскрытием цены. |
| Польза вопросов | Для каждого вопроса QA и аналитик, если доступны, отмечают адресата, понятность, наличие различимых вариантов и возможность составить тест после ответа. | Считать принятые, отклонённые, дубли и случаи, где ответ уже был в ТЗ. Внешние оценки и собственное ревью отмечать раздельно. |

Полнота = найденные уникальные эталонные дефекты / все подтверждённые эталонные дефекты. Точность = верные уникальные находки / все проверенные уникальные находки. Для пустого знаменателя писать «не применимо». Дополнительная обоснованная находка проходит независимую проверку до обновления эталона. По возможности скрыть от оценщика название метода. Закрепить версию эталона до сравнения, при изменении пересчитать все варианты.

## Что показать по четырём критериям

| Официальный вес | Доказательство для жюри |
|---|---|
| 25% — уточнения | Один точный вопрос владельцу, последствия каждого ответа и получившийся приёмочный сценарий. Показать случай, где агент уже нашёл ответ в тексте и не отвлекает человека. |
| 25% — архитектура | Раскрыть два фрагмента ТЗ, условия применимости, машинную проверку и границу её гарантий. Взять новый вход через CLI. |
| 25% — ценность | Показать решение для аналитика и тест для QA, одну ложную тревогу, которую агент отсеял, и фактическое сравнение с базовым подходом. |
| 25% — защита | На экране видны операция, два исхода и последствия решения. Жюри может открыть тот же автоматически созданный отчёт и повторить запуск по README. |

Официально опубликованы веса и названия критериев. Таблица задаёт нашу внутреннюю планку. Итоговые баллы присуждает жюри. [Оценка организаторов](https://bcchubagents.mnu.kz/)

## Порядок реализации и история Git

1. **Astra, контракт и эталон.** Зафиксировать интерфейсы, CLI, правила критичности, заранее заморозить набор оценки. Согласовать образец одной карточки и сценарий приёмки.
2. **Первая вертикальная версия.** Настоящий вызов LLM на незнакомом мини-ТЗ, реальные ссылки, автоматически созданный файл. Один проход всей системы выявит несовместимость интерфейсов сразу.
3. **Sol, независимые направления.** Первый чат владеет импортом и адресацией, второй — анализом и контрпримером, третий — интерфейсом решений и сравнением версий. Общий контракт меняется через интеграционный чат. Оценочные примеры доступны занимающемуся проверкой, рабочий агент открывает только переданный документ.
4. **Astra, интеграция и испытания.** Сверка отчёта с требованиями организаторов, слепые варианты, измерения, проверка чистого запуска. Публиковать паспорт реального прогона и ограничений.
5. **Защита.** Дублировать свежий живой показ сохранённым артефактом с явно указанным происхождением. Отрепетировать вопрос «что произойдёт, если я поменяю другое правило?». Для участников собрать презентацию, демо, исходный документ, отчёт, доступный жюри репозиторий и студенческий билет для закрытой формы. Контрольный срок команды — 27 ноября 21:30 по Астане, официальный — 23:59.

Естественная единица коммита — отдельно проверяемая возможность: реестр источников, первый живой прогон, смысловая проверка, экспорт отчёта, интерфейс решений, оценка, демонстрация. У каждого изменения есть понятный результат. Никаких заранее опубликованных метрик или обещаний по числу коммитов.
