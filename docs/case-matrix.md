# Разметка исходного кейса для проверки качества агента

Ручная аналитическая работа. Использовать для оценки и разбора расхождений. При генерации отчёта агент получает только документ и общие критерии качества. Эта таблица, номера строк, имена дефектов и эталонные ответы принадлежат контуру оценки.

Проверена [версия документа 928c1aa](https://github.com/BCC-HUB/ai-requirements-validator-task/blob/928c1aa364265426105b69ba7a3444eac11b22db/docs/requirements.md). В исходном Markdown 198 строк, 34 заголовка, 7 таблиц и 6 блоков JSON. Четыре номера Ф-1…Ф-4 обозначают группы правил. Количество атомарных требований определяется явным правилом разбиения. Строки далее указаны по Markdown в GitHub.

## Как трактовать результат

Доказанный конфликт требует двух правил с пересекающимися условиями и несовместимыми исходами. Для пробела достаточно зафиксированного обязательства и проверенной области поиска, где недостающий контракт должен был быть описан. Для вопроса достаточно назвать решение, которое пока нельзя принять. Возможный недостаток архитектуры, отсутствие подписи и неправильное поведение одной покупки имеют разный приоритет.

Для любой находки сопоставить источник, контекст, бизнес-эффект и конкретный вопрос. Два сообщения о D1 с разными словами дают одну находку. При исправлении календарного примера D1 должен исчезнуть, D2 сохраниться. Если в тестовом варианте специально исправлены обе стороны D2, оценивать это отдельно. Строки D8–D12 намеренно включают неоднозначные наблюдения и примеры, у которых часть ответа уже известна. Их нельзя автоматически считать обязательными ошибками для расчёта полноты.
