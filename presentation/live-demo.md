# Защита «Разбор ТЗ»

Системный аналитик отделяет решения, которые должен принять владелец карточного продукта, от сценариев, которые QA уже может проверить по ТЗ. На покупке через границу месяцев можно также вычислить последствия двух трактовок и испытать правку после ответа владельца. [Слайды с заметками](bcc-pitch.pptx) · [Видео, 58 секунд](bcc-demo.mp4)

## Какие действия записаны

В Chrome открыто рабочее место по одному официальному прогону. В видео видны навигация, ввод обоих ответов владельца и локальный пересчёт. Полное ревью, ответы модели и проверка новой редакции заранее выполнены и сохранены. Перед вводом уточнения в интерфейс восстановлен первый ход того же диалога. Ожидание модели вырезано. Озвучка синтезирована. SHA-256 базового JSON — `9a0a736a8a69e38a3965209e25c0fd4b89c2f4adffa45c9c17119f2983e95dae`. [Базовый запуск](../runs/bcc-release/review.json) · [Оба хода](../runs/bcc-release/owner/dialogue.html) · [Перепроверка](../runs/bcc-release/owner/wrong-revision.html)

| Время | Экран и действие |
| --- | --- |
| 0–9 с | Отчёт открыт в браузере. При первой настройке уведомления выключены, порог не задан. Клиент пытается сохранить это состояние. От владельца требуется решение о допустимости действия и представлении пустого порога. |
| 9–16 с | Для следующего сценария исход задан. При сравнении с порогом QA может отличить сумму на один тиын ниже порога от точного достижения. |
| 16–22 с | В рабочем месте одна покупка через границу месяца даёт два исхода по действующим правилам. |
| 22–28 с | В окне расчёта меняются входные данные. Обе трактовки пересчитываются локально. |
| 28–33 с | Владелец вводит третий вариант — отдельный счётчик «Переходящие». |
| 33–39 с | Восстановлен первый подлинный ход. Агент показывает свой довопрос и ранее подтверждённую часть. |
| 39–46 с | В поле ответа на этот довопрос вводится уточнение для разных и совпадающих месяцев. |
| 46–50 с | В сохранённой переписке новое правило готово к проверке. |
| 50–58 с | В новой редакции пример на стыке исправлен. Для покупки внутри месяца текст всё ещё предписывает двойное начисление. Замечание открыто. |

## Показ за 90 секунд

Запустите из корня репозитория `python3 -m reviewer.serve` и откройте выведенный адрес. Для автономного показа откройте HTML-файлы с диска. Новый ответ модели при живом обсуждении требует настроенного провайдера. [Рабочее место](http://127.0.0.1:8765/) · [Автономный HTML](../runs/bcc-release/review.html) · [PDF](../runs/bcc-release/review.pdf)

| Время | Что открыть и сказать |
| --- | --- |
| 0–20 с | Откройте «Сценарии для QA» и выберите «Первое действие». «Клиент впервые открывает настройки, оставляет уведомления выключенными и поле пустым и нажимает “Сохранить”. По ТЗ неясно, должна ли попытка дойти до API. Этот вопрос идёт владельцу». [Первое действие](../runs/bcc-release/review.html#qa-scenario-1) |
| 20–35 с | Выберите «Граница значения». «Здесь исход уже следует из правил. До порога не хватает одного тиына — push ещё не приходит. На пороге — приходит». Покажите условия независимых прогонов и две суммы. [Граница значения](../runs/bcc-release/review.html#qa-scenario-4) |
| 35–55 с | Откройте D-01, строки 38 и 64. «Покупку на 4 000 ₸ сделали 31 января, а провели 1 февраля. Код посчитал февральский итог по обеим трактовкам». В исходном примере 0 / 4 000 ₸. На контрольном вводе обе трактовки дают 4 000 ₸. [Расчёт](../runs/bcc-release/review.html#execution-D-01) |
| 55–75 с | Нажмите «Ответить своими словами». Для показа без ожидания раскройте «Посмотреть сохранённый пример без модели» и нажмите «Прочитать диалог». Сначала владелец называет третий счётчик. Затем уточняет его поведение для двух случаев. [Переписка](../runs/bcc-release/owner/dialogue.html) |
| 75–90 с | Откройте проверку правки. «На границе месяцев исход верен. Внутри одного месяца документ по-прежнему дублирует начисление. Владелец видит строку, QA — второй случай». Завершите предложением пилота на двух обезличенных ТЗ. [Перепроверка](../runs/bcc-release/owner/wrong-revision.html) |

## Вопросы и реплики дословно

**Первое сохранение.** Доступно ли первое сохранение при выключенном уведомлении и пустом пороге и, если да, каким запросом приложение должно передать отсутствие порога? [Сценарий и цитаты](../runs/bcc-release/review.html#qa-scenario-1)

**Первый ответ владельца по месяцу покупки.** Для покупок на стыке месяцев завели отдельный счётчик «Переходящие». Это точно.

**Довопрос агента.** Если все три счётчика были на нуле, какие суммы покажут «Переходящие», январь и февраль после проведения 1 февраля покупки на 4 000 ₸ от 31 января?

**Уточнение владельца.** Когда месяц покупки и проведения по Алматы различается, после проведения вся сумма идёт только в «Переходящие». Январь и февраль по этой покупке остаются без изменений. Если оба события в одном месяце, вся сумма идёт только в обычный счётчик этого месяца. В «Переходящие» в этом случае ноль. [Машиночитаемый диалог](../runs/bcc-release/owner/dialogue.json)

## Ещё три ситуации из того же отчёта

| Ситуация | Вопрос или ожидаемый исход |
| --- | --- |
| Сбой и повтор события | Вопрос владельцу. Должна ли повторная обработка обеспечить один push, если признак уже зафиксирован, а передача до сбоя не состоялась, или в этом случае допустим пропуск? [Исходные строки](../runs/bcc-release/review.html#qa-scenario-2) |
| Возврат и повторное пересечение | Ожидание для QA. При повторном достижении 50 000 ₸ второго push нет. Всего по карте за месяц получен один push. [Исходные строки](../runs/bcc-release/review.html#qa-scenario-3) |
| Две карты одного клиента | Ожидание для QA. Карта А — всего 1 push за месяц. Карта Б — всего 1 push за месяц. [Исходные строки](../runs/bcc-release/review.html#qa-scenario-5) |
