# Холодная проверка резерва через две формы

В переплётной мастерской надпись на талоне определяет следующий производственный участок. Терминал выбирает участок по толщине корешка. Подготовлены две синтетические спецификации с разными названиями и порогами. Через каждую форму загружается только соответствующий Markdown-файл.

| Путь | Документ | SHA-256 загружаемых байтов | Ожидаемое поведение |
|---|---|---|---|
| Публичный сайт, «Запустить проверку» | `bindery-site.md` | `ae8fb9194865549f33a06e213b6b421c4f94ddfef1fb83c5e35b14daa24b2295` | Для 18 мм строка 4 предписывает швейный участок, строка 11 — клеевой. Нужен вопрос владельцу, какую надпись печатать на границе. Для 17 мм строка 10 согласуется с правилом. |
| Чистый локальный запуск, «Проверить через сервер проекта» | `bindery-local.md` | `25a54aa29e17c3de0d24dd1d2adaf76d100671dcbf74df26b9cc528c200a38d4` | Для 23 мм те же строки расходятся по участку. Вопрос должен касаться именно этой границы. Для 22 мм строка 10 согласуется с правилом. |

Успех доставки требует нового задания через соответствующую кнопку и полного отчёта с заданным SHA-256 исходника. В паспорте ожидаются хотя бы одно новое обращение, `cloudflare-workers-ai` и переход с `gemini-api` после HTTP 429. Проверяем сохранённые HTML и JSON вместе с цитатами. Дополнительно оцениваем обнаружение размеченного противоречия и отсутствие ложного противоречия на контрольной строке. Ошибки доставки и ошибки качества записываем отдельно.

## Запуск

Из корня репозитория выполните команды по очереди. Нужны Python с зависимостями проекта и Playwright с Chromium или Chrome. Для внешней установки можно задать `PLAYWRIGHT_PACKAGE`, `CHROME_BINARY` и `PYTHON`. Каждому прогону нужен новый каталог результатов.

```sh
node eval/hosted-reserve/browser.mjs site output/bindery-site-1
node eval/hosted-reserve/browser.mjs local output/bindery-local-1
```

Сайт открывается в чистом браузерном контексте. Для локальной проверки сценарий клонирует текущий коммит во временный каталог, проверяет чистоту дерева и запускает приложение на свободном порту без ключей моделей. Обе формы должны дать HTTP 202, опросить статус своего задания и показать ссылку на его результат. Каждый путь отправляет документ на действующий сервер один раз.

Файлы `review.json` и `review.html` содержат ответ приложения, `browser.json` — квитанцию браузера, `audit.json` — результат проверки содержимого. При отказе формы или недоступности сервера причина сохраняется в `browser.json`. Код завершения 0 требует успешной доставки и обнаружения размеченного расхождения. Для повторной оценки уже скачанных файлов достаточно Python.

```sh
python3 -m eval.hosted-reserve.verify site output/bindery-site-1
python3 -m eval.hosted-reserve.verify local output/bindery-local-1
```

Локальная репетиция проверяет кнопки, байты отправленного файла и отказ на заведомо чужом архивном отчёте. Обе формы в этом тесте обслуживает временный сервер на loopback. Чтобы проверить сам сценарий без обращений к модели, выполните `node eval/hosted-reserve/offline.mjs`.
