# Работа аналитика с результатами проверки

## Когда аналитик исправил ТЗ

В рабочем месте раздел «Согласование» открывает первый критический конфликт из завершённого полного прогона. До загрузки собственного документа доступен официальный пример. У вопроса агента показаны два фрагмента исходника. Для цитаты из таблицы отображаются имена столбцов. Аналитик сравнивает допустимые исходы, выбирает один и копирует черновик критерия приёмки. Ссылка на строку ведёт в полный отчёт. Если владелец согласовал исход, нажмите «Зафиксировать решение владельца». Теперь перепроверка показывает два вывода — исчезло ли противоречие и соответствует ли исправленный текст согласованному исходу. Исход можно заменить или отменить. Решения хранятся в этой вкладке и привязаны к SHA-256 базового JSON.

В полном HTML-отчёте у критического противоречия с подтверждённым сценарием откройте «Подготовить критерий приёмки для QA». Выберите один из исходов, чтобы увидеть черновик с операцией, ожидаемым результатом и ссылкой на правило. Владелец продукта согласует решение, а аналитик вносит его в исходный документ.

Сохраните исходное полное ревью как JSON. Передайте его вместе с новой версией ТЗ, чтобы получить статус каждого прежнего критического замечания, новые цитаты и изменения строк. Для адресной проверки отдельного замечания добавьте `--finding D-01`. Параметр можно повторять.

```sh
python3 -m reviewer.recheck output/review.json revised.md output/recheck.json
python3 -m reviewer.render output/recheck.json output/recheck.html
```

В браузере выберите «Проверка новой версии», укажите базовый отчёт и раскройте «Замечания». Можно отметить проблемы любого приоритета. Пустой выбор запускает проверку всех критических замечаний базы. Чтобы найти новые дефекты, запустите полное ревью новой версии.

Через CLI добавьте `--decision D-01=first` (либо `second`) и `--baseline-sha256` с SHA-256 **файла полного отчёта**. Стороны относятся к `first` и `second` в подтверждённом сценарии этого замечания. Модель определяет поведение новой редакции по тексту. Код отдельно сравнивает его с выбором владельца. Если в новой версии остаются допустимыми оба исхода, соответствие помечается «не подтверждено». [Две согласованные редакции и реальные результаты](../eval/owner-decision/README.md)

### Если владелец отвечает своими словами

В рабочем месте откройте «Ответ владельца», выберите замечание и напишите, какое поведение уже согласовано. Можно предложить другую политику, ответить на часть вопроса или пересмотреть прежний ответ. Агент сохраняет реплики и подтверждённые условия. Если для проверяемого правила не хватает решения, он задаёт один довопрос. Когда правило сформулировано, замечание остаётся открытым до проверки новой редакции. Переписка доступна после обновления страницы, пока работает локальный сервер. Чтобы вернуться к ней после перезапуска, нажмите «Скачать диалог · JSON» и передайте файл в CLI через `--previous`.

Кнопка «Проверить новую версию ТЗ» выбирает то же замечание. Адресная проверка сначала оценивает исходную проблему по тексту документа. Для полного ответа отдельный модельный проход сверяет каждое согласованное условие с новой редакцией. Итог «Замечание закрыто» требует устранения исходной проблемы, подтверждения всех условий и ссылки на относящуюся к исправлению строку. Частичный ответ, отсутствующее условие или противоречие оставляют замечание открытым.

Тот же диалог доступен через CLI. В следующей команде `SHA` вычисляется по полному JSON-отчёту. Файлы ходов можно сохранить и передать следующему аналитику.

```sh
BASE=runs/bcc-submission/review.json
SHA=$(shasum -a 256 "$BASE" | cut -d ' ' -f 1)
python3 -m reviewer.clarify "$BASE" --finding D-01 --baseline-sha256 "$SHA" \
  --answer 'Для покупок на стыке месяцев завели отдельный счётчик «Переходящие».' --out output/turn-1.json
python3 -m reviewer.clarify "$BASE" --finding D-01 --baseline-sha256 "$SHA" \
  --previous output/turn-1.json --answer 'При разных месяцах по Алматы вся сумма после проведения идёт только в «Переходящие». При совпадении месяцев сумма идёт только в этот месяц.' --out output/turn-2.json
python3 -m reviewer.recheck "$BASE" eval/freeform-owner/complete.md output/check.html \
  --finding D-01 --baseline-sha256 "$SHA" --clarification output/turn-2.json
```

Учебный третий вариант и контроль с двойным начислением показаны в [результатах реального прогона](../eval/freeform-owner/README.md). Есть также [пример уточняющего вопроса по REST API в рабочем месте](../eval/freeform-owner/workbench/d08-follow-up.png).

В [примере с резервом продавца](../runs/targeted-recheck/README.md) проверяется исправление фамилии из паспорта ТЗ. Полное ревью и адресная перепроверка выполнены через рабочий сервер.

Совпадение хеша входа позволяет подтвердить исходный результат локально. Для MD и TXT это также работает после пересохранения с BOM или другими окончаниями строк, если проверяемые строки и их адреса точно совпадают. В паспорте отдельно видны совпадение файла по байтам, совпадение текста и фактическое число обращений к модели.

## Как проверяется покрытие

В ходе полного ревью рабочее место показывает число проверенных групп строк из запланированных. Группа засчитывается после проверки ответа и цитат. Сверка требований по всему документу начинается после локальных проверок и поиска сценариев. Время ответа модели на каждой стадии может различаться.

1. Парсер сохраняет диапазон строк каждого блока. Строка таблицы связана с заголовками столбцов, блок JSON — с разделом и строками исходника. Разделители Markdown, заголовки и шаблоны отражены в карте покрытия.
2. Независимые запросы обрабатывают группы блоков с доступом к полному исходному тексту. Каждый содержательный блок должен получить классификацию. Составные правила делятся на отдельно проверяемые пункты. У каждого есть внутренний ID, исходный ID при наличии, роль, формулировка, конкретная проверка и дословная цитата. Приёмочные и контрактные примеры считаются отдельно от нормативных требований.
3. Отдельный проход ищет сценарии, в которых две трактовки дают разные результаты. Последний проход видит весь текст, реестр и эти сценарии, проверяет совместимость правил, объединяет проявления одной проблемы и обосновывает решение о каждом локальном замечании. Область оценки включает полноту, согласованность, проверяемость, прослеживаемость и границы решения.
4. До записи проверяются исходные цитаты, присутствие всех блоков, разрешение всех локальных замечаний и судьба каждого кандидата в конфликт. Сводка HTML и PDF вычисляется из уникальных итоговых записей. Модель описывает предмет исправления и приводит свидетельства. Код вычисляет приоритет по версионированной шкале и повторно проверяет его при открытии отчёта. Сбой стадии завершает команду с ошибкой, существующий финальный файл сохраняется.

В полных отчётах со шкалой `impact-v1` критический приоритет требует одного сценария, двух несовместимых результатов продукта и двух подтверждающих фрагментов ТЗ. Существенный приоритет получают проблемы реализации, интеграции и приёмки. Редакционный получают правки, которые меняют только документ. В карточке замечания раздел «Основание приоритета» показывает применённое правило. У уже сохранённых отчётов сохраняется исходная оценка.

Модель работает в отдельном временном каталоге с отключёнными инструментами и памятью. Параметр `--checkpoint-dir /путь/к/кэшу` сохраняет подтверждённые стадии локально. Ключ учитывает модель, схему, запрос и контрольную сумму движка. При возобновлении агент заново проверяет каждую сохранённую стадию, а повреждённую вычисляет снова. В паспорте `fresh_calls` и `current_usage` описывают новые обращения в этом запуске, `restored_attempts` — восстановленную историю. Поле `usage` сохраняет суммарный расход всех попыток исходного анализа. В контрольных точках есть результаты анализа документа.

Независимые стадии полного ревью выполняются параллельно. По умолчанию допускаются шесть одновременных запросов. Параметр `--workers 1` включает последовательный режим. Паспорт прогона показывает лимит, длительность каждой попытки и общий расход токенов.

## Совместимость и испытания

Для прежнего быстрого режима поиска поведенческих противоречий использовать `--conflicts-only`. Его отчёты версии 1 по-прежнему открываются. Команда дополнительного заключения для версии 1 — `python3 -m reviewer.challenge <review.json> <second-opinion.json>`. Полный режим использует версию 2 и уже включает итоговую проверку кандидатов.

```sh
python3 -m unittest discover -s tests -v
```
