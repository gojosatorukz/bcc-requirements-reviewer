# Скорость полного ревью при сохранении проверяемых результатов

Протокол составлен до сравниваемых новых запусков. База — три сохранённых холодных результата GPT-6.2 Astra через обычный Codex CLI, версия движка `67991fe555a3`. Используем те же исходные байты, модель, провайдер и число исполнителей, записанное в каждом базовом JSON (6 у BCC, по 4 у обеих версий планетария). Каждый новый полный запуск начинается без восстановленных ответов: успешный выход, SHA документа и `restored_attempts=0` проверяем отдельно. Ошибки лимита или транспорта с отсутствующим результатом укажем отдельно от отрицательного качественного результата. Периодически изменяющаяся загрузка провайдера остаётся источником вариативности. Новый официальный запуск выполняет команда выпуска. Сравнение дополнено двумя независимыми запусками по планетарию.

| Документ | SHA-256 исходника | Базовый SHA-256 JSON | Секунды | Вызовы / отклонённые попытки |
|---|---|---|---:|---:|
| BCC | `e7dae55e5453a250d93e335f5ff9c7f775f4457ccddd333f4a67e47b20d74381` | `460c1efdc009a25f22d4f14f331a3734622b71678099def151e0cb0e076fae2b` | 410,60 | 17 / 2 |
| Планетарий | `44e6c8a3b50c68361093d6595670b306930254ea297897cdaca9695e63bd821f` | `9cc18fcfef3ba8250afad06214f7d8f0078657fa61a369d2c1634e2e5ca0b839` | 160,45 | 7 / 0 |
| Согласованный планетарий | `dd7c19cbfd5746fe5591d27406887bfeb5f04807c429337ba2a9a3b36002ff2a` | `7aca043079cba9b9b027437f4e2c20a7bce7d94e7dc248d4169336c3a26f7a1a` | 190,54 | 7 / 0 |

Время до готового отчёта берём из `run.elapsed_seconds`. Для каждой пары указываем абсолютное изменение, отношение нового времени к базовому, число новых обращений, отклонённых попыток и их причины. Распределение времени по стадиям восстановим из кода проверяемого SHA и сохранённых длительностей отдельных обращений. У базовой версии очередь сценариев/полей/блоков общая для выделенных исполнителей, после неё согласование всего документа и QA идут последовательно. Независимые замечания затем исполняются параллельно, внутри каждой ветви предложение, проверка смысла и исправление зависят друг от друга. Повтор входит во время своей стадии. Сумма секунд всех модельных обращений учитывает параллельную работу, поэтому отдельно приводим календарное время. При отсутствии времён старта каждой попытки помечаем расчёт критического пути как реконструкцию. Сверх этих трёх измерений статистической гарантии ускорения не выводим.

## Сохранение качества

1. По [матрице BCC](../../docs/case-matrix.md) перечитываем все D1–D12 и C1–C14 в новом отчёте, проверяем цитаты, регистр, сообщения QA, приоритеты и ход вычислений по каждой теме. Базой служит [аудит в зафиксированном коммите](https://github.com/gojosatorukz/bcc-requirements-reviewer/blob/4845a4d/eval/official-coverage/release.md). Полно / частично / пропуск / ошибка выставляем отдельно, открытый вопрос остаётся вопросом. «26/26» относится исключительно к внутренней матрице, баллы жюри не прогнозируются.
2. У D12 вопрос владельцу в `whole.findings[].question` должен явно называть `result` и 400/401/404/500, содержимое тела каждой ошибки сверяем с источником. Идентификатор D-15 относится к базовому JSON и может измениться. Таблица примеров или текст совета без вопроса недостаточны.
3. На исходных парах BCC (38/64, 39/40) нужны реальные исполненные программы с совпадающими контролями и соответствующими февралю 0/4 000 ₸ и 1/2 push исходами. Вопрос о чтении исходного состояния не допускает моделирования двух истинных ответов на переданный сохраняющий GET. Отдельно ищем дополнительные ошибочные утверждения.
4. Сверяем все пять [ситуаций жизненного цикла](../lifecycle/protocol.md): первый выключенный режим+пустая сумма, повтор после неопределённого исхода передачи, повтор после возврата с прежним порогом, один тиын ниже, независимость карт одного клиента в тот же месяц. Проведённые тесты и предложенные сценарии различаем.
5. На планетарии воспроизводим [слепой оракул](../field-obligations/protocol.md). Нужно 15/15 верных нормативных ошибочных комбинаций на каждом документе. Исходный вариант должен адресовать владельцу вопрос про nextStep отдельно для POST 409 и POST 503. В согласованном 409 ключ исключён, 503 обязателен, соответствующих ложных вопросов нет. В GET 409 одноимённый ключ обязателен в обеих версиях. Проверяем шесть фактических тел и прямые основания; формат тела в GET нельзя переносить на POST.
6. По каждому входу сохраняем новый JSON с SHA. Если улучшение времени сопровождается недостающими гарантиями или ложными выводами, сообщаем оба результата. Единичный быстрый повтор после неудачи не заменяет исходную попытку.

После регистрации протокола число исполнителей сверено напрямую в трёх старых `run.max_workers`. Шесть для BCC, четыре для каждого планетария. Поправка к описанию сделана до получения любого нового результата.
