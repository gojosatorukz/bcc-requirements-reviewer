## Что изменилось в выводе агента

В предыдущем JSON карточка D-13 спрашивала владельца об `amount` и `enabled` при отклонении суммы. В реестре можно было самостоятельно найти тела четырёх ошибок с одним `message`. Вопрос о гарантии `result` для этих четырёх исходов появился только при формировании печатного представления. До нового запуска зафиксировали условие зачёта — вопрос должен появиться в `whole.findings[].question` и назвать поле и каждый статус. [Предыдущая оценка 25/26](https://github.com/gojosatorukz/bcc-requirements-reviewer/blob/987e99a150942d3fd16df62f033b41630d56a0f2/eval/official-coverage/release.md) · [Предыдущий сырой JSON](https://github.com/gojosatorukz/bcc-requirements-reviewer/blob/987e99a150942d3fd16df62f033b41630d56a0f2/runs/bcc-release/review.json) · [Условие до нового прогона](https://github.com/gojosatorukz/bcc-requirements-reviewer/blob/e5a9047e6c87365b89dc33cf94a9ffb86c8a6752/eval/official-coverage/release.md)

**Вопрос D-15 в новом JSON**

> Каков статус каждого из полей `result` и `enabled` (обязательно, необязательно или исключено) отдельно для HTTP 400 при неверных параметрах, HTTP 401 без авторизации, HTTP 404 для чужой или отсутствующей карты и HTTP 500 при внутренней ошибке?

Проверены все семь цитат карточки. Строки 155 и 157 задают назначение полей. Строки 180, 185, 192 и 197 содержат четыре тела с единственным ключом `message`. Именно строка 190 маркирует третье тело кодом 404. Строка 188 озаглавлена 403, и область применения этого статуса отдельно уточняется в D-16. Прикладной отказ под HTTP 200 содержит `result="ERROR"` и `message` в строке 171. Его статус и способ вернуть старую настройку отдельно разобраны в D-12 и D-13. [Карточка D-15](../../runs/bcc-release/review.html#D-15) · [Прикладной отказ](../../runs/bcc-release/review.html#source-line-171)

В `response_field_review` для каждой из четырёх HTTP-ошибок одинаковы следующие решения. У `result` и `enabled` правила присутствия не определены. Для `amount` модель ссылается на условие «При успехе» в строке 156 и отмечает поле как исключённое из описанных ошибочных исходов. Для `message` условие «При ошибке» в строке 158 даёт обязательное поле. Для двух полей с определённой областью агент не задаёт владельцу повторный вопрос. Ни по одному из четырёх полей одно только отсутствие ключа в примере не служит нормативным основанием. [Состав ответов](../../runs/bcc-release/review.html#response-fields)

## Проверка глазами аналитика

В настоящем Chrome предыдущий и новый JSON поочерёдно открыты через «Открыть сохранённый отчёт». В форме ответа владельца выбрана соответствующая карточка. Текст D-15 дословно совпал в форме, полном HTML и скачиваемом JSON. Все семь ссылок из карточки привели к нужным цитатам в исходнике, SHA-256 полученных байтов совпал с оригиналом. Все пять сценариев QA переключены на ширинах 320, 412 и 1440 пикселей с переходом к полному отчёту. Открытие старого отчёта без раздела QA убирает представление предыдущих сценариев. В ходе этих действий модель не вызывалась.

Просмотрены растровые изображения всех 46 страниц PDF. На первой странице видны вопросы владельцу и результаты 0 / 4 000 ₸ и 1 / 2 push. Таблица состава ответов занимает страницы 13–14, все имена ключей помещаются в колонке, при переходе повторяется заголовок.
