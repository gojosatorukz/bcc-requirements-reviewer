# Что изменилось в проверке бизнес-правил Gemini

На одном и том же официальном ТЗ Gemini 3.5 Flash-Lite раньше пропустил оба контрольных конфликта. После изменения ядра оба стали отдельными критическими замечаниями. Модель получает текст загруженного документа. Эталон с ожидаемыми строками используется только для проверки готового JSON. [До](../bcc-flash-lite.json) · [Отчёт релиза в HTML](bcc-release.html) · [Исходный JSON релиза](bcc-release.json) · [Протокол](protocol.md)

В холодном прогоне версии `3fa071c41274` D-01 спрашивает, какой месяц получит покупку на границе января и февраля. В D-02 владелец выбирает между одним и двумя уведомлениями за календарный месяц, а в D-06 решает обязательность `result` для всех четырёх приведённых ошибок. Прогон занял 133,13 с и потребовал 24 новых обращения. Для обоих критических замечаний статус исполнения программы — `unsupported`. [Полный JSON](bcc-release.json)

Для ложного срабатывания добавлена независимая проверка: когда итоговое замечание оспаривает согласованный пример, агент повторно сравнивает исходы именно этого замечания по единому списку значений. На сохранённых ответах Google локально проверено, что спорные строки 5 и 15 попадают в эту проверку. Модульные тесты охватывают совпадение, расхождение и частичную применимость. Живой ответ Google на дополнительный этап пока не получен.

27 ноября около 17:07 по Астане Google вернул HTTP 429 для Flash-Lite, суточный лимит данного проекта 500 запросов и ожидание 71 558 секунд. Поэтому повтор последней правки, дополнительная пара про корпоративные платежи и новый веб-прогон официального ТЗ остались без полного отчёта на этой версии. На сайте сохранённый официальный Gemini HTML и JSON открываются без обращения к провайдеру. В конфигурации размещения используется тот же серверный профиль. [Протокол](protocol.md) · [Инструкция запуска](../../../README.md)

## Исправление ложной блокировки музея

В сохранённом отчёте Gemini D-01 запретил принять передачу паспорта. Строка 5 сохраняет закрепление за отправителем. Строка 15 оставляет паспорт в очереди Северной мастерской, которая его отправила. Строка 6 связывает очередь с закреплением. Прогноз по правилам и отдельная сверка приёмки уже согласились между собой. [Исходное замечание](museum-aligned-release.json) · [Ответы двух стадий](museum-aligned-stage-outputs.json)

В версии `b47dbbd` сверяющий читает ТЗ, сценарий и вопрос. Предыдущие расчёты и вердикты моделей ему не передаются. Он указывает две дословные цитаты и значения одного показателя. Код проверяет цитаты по их собственным строкам. Снятие замечания требует совпадения значений и полного охвата вопроса. Карточка, объединяющая разные пары источников, сохраняется. После снятия агент заново оценивает пять свойств ТЗ, готовность к разработке и готовность к тестированию.

| Контроль | Критические замечания до → после | Что воспроизвёл сверяющий |
|---|---|---|
| [Исправленный музей](precision/museum-aligned.json) | 1 → 0 | По обеим строкам паспорт остаётся у Северной. Причина снятия попала в историю. По разработке и тестированию теперь «можно начинать». Для реализации непустого `frames` отдельно отмечен неизвестный формат элемента. |
| [Официальное банковское ТЗ](precision/bcc.json) | 2 → 2 | Январь или февраль. Один или два push за месяц. Вопрос D-06 о `result` для 400, 401, 404 и 500 сохранён. |
| [Исходный музей](precision/museum.json) | 2 → 2 | Северная или Южная. Только A2 или обе редакции. Вторая карточка также спрашивает о хранении истории. Судья установил расхождение в видимости, а для хранения отметил неполный охват. |

**Как получены цифры.** «До» — полные отчёты Google Gemini 3.5 Flash-Lite. «После» — повтор именно изменённых стадий ядра на тех же ответах, с живым независимым сверяющим GPT-6.2 Astra. На исправленном музее использован подлинный сигнал о согласии двух исходов. На исходном музее и в банковском ТЗ поданы четыре заведомо ложных сигнала о согласии. Ни один не снял настоящее замечание. Три случая сверяющий разобрал полностью, один частично. В первой попытке на исходном музее оба замечания также сохранились, но проверочный скрипт отклонил частичный охват и не сохранил сырой ответ. В приведённом повторе запись идёт сразу после стадии. [Условия, записанные до исправления](precision-protocol.md)

Для новых полных запусков на обоих ТЗ использовали обычный CLI и пустой каталог контрольных точек. Google ответил HTTP 429 на стадии «Сценарии» обоих запусков после изменения. Подтверждён суточный лимит 500 запросов для этой модели в проекте. Полного холодного отчёта исправленной версии от Google пока нет. В публичной конфигурации сверяющий использует ту же Gemini, что и остальной прогон. Astra использована в этом эксперименте.

Повтор всей таблицы без сети и ключа из корня репозитория:

```sh
python3 -m eval.gemini.behavior.precision museum-aligned bcc museum
```

Команда сверяет хеши исходных отчётов, входы и схемы сохранённых стадий, цитаты, судьбу каждого кандидата и итоговые банковские вопросы. Для свежего сравнения после восстановления квоты команды полного запуска приведены ниже.

Второй холодный запуск той же промежуточной версии через загрузку на сайте занял 143,90 с. В поиске сценариев агент получил один и два push, затем в итоговой сверке объявил правила совместимыми. В одном из последующих холодных веб-прогонов Gemini построил исполняемый пример для повторного уведомления. Интерпретатор получил первое расхождение на втором шаге: значение `push_count` равно 1 и 2. Оба целевых конфликта вошли в отчёт за 125,75 с. В этом конкретном прогоне вопрос об обязательности `result` был потерян. Строка соседнего поля с описанием условия ошибки была ошибочно принята за условие присутствия `result`. [Исходный отчёт с программой и контрольной трассой](bcc-push-executed.json)

## Какие проверки выполняет агент

Агент временно скрывает колонку с ожидаемым результатом приёмочного примера и выводит результат из правил. Затем сравнивает прогноз с исходной ячейкой. Для количественного ограничения он начинает со значения на границе и по второй норме проверяет, сколько новых событий или действующих объектов добавляется. Уже произошедшее событие сохраняется в числе событий того же периода. Для выбытия действующего объекта нужна цитата об окончании его действия. Владелец получает общий сценарий, оба результата и ссылки на строки.

## Что видит владелец банковского продукта

- **Месяц покупки, строки 38 и 64.** Покупку на 4 000 ₸ совершили 31 января в 23:58, провели 1 февраля в 00:03. По правилу сумма идёт в январь, по таблице приёмки — в февраль. В карточке D-01 агент спрашивает, в каком месяце учесть эту покупку.
- **Повторный push, строки 39 и 40.** За месяц уже был push. После изменения порога расходы ниже нового порога и затем достигают его ещё раз. При месячном ограничении клиент получит один push за месяц, при повторной отправке — два. В D-02 владелец решает, разрешено ли второе уведомление.

Эти результаты проверены по цитатам и описанным исходам в сохранённом отчёте. В этом официальном прогоне для машинного воспроизведения D-01 и D-02 Gemini вернул `unsupported`. Сохранённый конкурсный отчёт Astra содержит исполняемые программы для обоих. [Результат Astra](../../../runs/bcc-release/README.md)

## Как воспроизвести

Пример запуска из корня проекта при настроенном серверном `GEMINI_API_KEY`. Для каждого нового независимого замера нужен новый либо пустой каталог контрольных точек.

```sh
export REVIEW_PROVIDER=gemini REVIEW_MODEL=gemini-3.5-flash-lite
python -m reviewer submission/requirements.md output/bcc.json --workers 1 --checkpoint-dir output/bcc-new-cache
python -m eval.gemini.behavior.audit bcc output/bcc.json
python -m reviewer.render output/bcc.json output/bcc.html
```

Сохранённые отчёты можно проверить без ключа. Аудит сверяет SHA исходного ТЗ, структуру отчёта, приоритеты, цитаты с номерами строк и наличие вопроса владельцу. Для исправленных документов отдельно проверяются нарушения по контрольным парам. [Код проверки](audit.py)

```sh
for case in bcc museum museum-aligned workorder workorder-aligned; do
  python -m eval.gemini.behavior.audit "$case" "eval/gemini/behavior/$case-after.json" || exit 1
done
```

Для проверки последней живой серии используйте суффикс `-release.json`. На `museum-aligned-release.json` аудит возвращает код 1 и указывает ложное критическое замечание.
