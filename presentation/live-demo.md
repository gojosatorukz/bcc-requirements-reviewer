# Защита «Разбор ТЗ»

Системный аналитик отделяет решения, которые должен принять владелец карточного продукта, от сценариев, которые QA уже может проверить по ТЗ. На покупке через границу месяцев можно также вычислить последствия двух трактовок и испытать правку после ответа владельца. [Слайды с заметками](bcc-pitch.pptx) · [Видео, 69 секунд](bcc-demo.mp4)

## Какие действия записаны

В Chrome открыто рабочее место нового официального прогона. Для короткого сравнения показан экран поиска в предыдущем отчёте. В видео видны навигация, ввод обоих ответов владельца и локальный пересчёт. Полное ревью, ответы модели и проверка новой редакции заранее выполнены и сохранены. Перед вводом уточнения в интерфейс восстановлен первый ход того же диалога. Ожидание модели вырезано. Озвучка синтезирована. SHA-256 базового JSON — `460c1efdc009a25f22d4f14f331a3734622b71678099def151e0cb0e076fae2b`. [Базовый запуск](../runs/bcc-release/review.json) · [Оба хода](../runs/bcc-release/owner/dialogue.html) · [Перепроверка](../runs/bcc-release/owner/wrong-revision.html)

| Время | Экран и действие |
| --- | --- |
| 0–9 с | Отчёт открыт в браузере. При первой настройке уведомления выключены, порог не задан. Клиент пытается сохранить это состояние. От владельца требуется решение о допустимости действия и представлении пустого порога. |
| 9–16 с | Для следующего сценария исход задан. При сравнении с порогом QA сравнивает месячный итог на один тиын ниже порога с точным достижением. |
| 16–20 с | В архивном отчёте поиск по result не находит отдельного вопроса. В печатном отчёте подсказка уже существовала. |
| 20–27 с | Тот же поиск на новом прогоне открывает вопрос владельцу о поле result, дословно взятый из итогового JSON. |
| 27–33 с | В рабочем месте одна покупка через границу месяца даёт два исхода по действующим правилам. |
| 33–39 с | В окне расчёта меняются входные данные. Обе трактовки пересчитываются локально. |
| 39–44 с | Владелец вводит третий вариант — отдельный счётчик «Переходящие». |
| 44–50 с | Восстановлен первый подлинный ход. Агент показывает свой довопрос и ранее подтверждённую часть. |
| 50–57 с | В поле ответа на этот довопрос вводится уточнение для разных и совпадающих месяцев. |
| 57–61 с | В сохранённой переписке новое правило готово к проверке. |
| 61–69 с | В новой редакции пример на стыке исправлен. Для покупки внутри месяца текст всё ещё предписывает двойное начисление. Замечание открыто. |

## Показ за 90 секунд

Запустите из корня репозитория `python3 -m reviewer.serve` и откройте выведенный адрес. Для автономного показа откройте HTML-файлы с диска. Новый ответ модели при живом обсуждении требует настроенного провайдера. | Время | Что открыть и сказать |
| --- | --- |
| 0–20 с | Откройте «Сценарии для QA» и выберите «Первое действие». «Клиент впервые открывает настройки, оставляет уведомления выключенными и поле пустым и нажимает “Сохранить”. По ТЗ неясно, должна ли попытка дойти до API. Этот вопрос идёт владельцу». [Первое действие](../runs/bcc-release/review.html#qa-scenario-1) |
| 20–35 с | Выберите «Граница значения». «Здесь исход уже следует из правил. До порога не хватает одного тиына — push ещё не приходит. На пороге — приходит». Покажите условия независимых прогонов и две суммы. [Граница значения](../runs/bcc-release/review.html#qa-scenario-4) |
| 35–55 с | Откройте D-01, строки 38 и 64. «Покупку на 4 000 ₸ сделали 31 января, а провели 1 февраля. Код посчитал февральский итог по обеим трактовкам». В исходном примере 0 / 4 000 ₸. На контрольном вводе обе трактовки дают 4 000 ₸. [Расчёт](../runs/bcc-release/review.html#execution-D-01) |
| 55–75 с | Нажмите «Ответить своими словами». Для показа без ожидания раскройте «Посмотреть сохранённый пример без модели» и нажмите «Прочитать диалог». Сначала владелец называет третий счётчик. Затем уточняет его поведение для двух случаев. [Переписка](../runs/bcc-release/owner/dialogue.html) |
| 75–90 с | Откройте проверку правки. «На границе месяцев исход верен. Внутри одного месяца документ по-прежнему дублирует начисление. Владелец видит строку, QA — второй случай». Завершите предложением пилота на двух обезличенных ТЗ. [Перепроверка](../runs/bcc-release/owner/wrong-revision.html) |

## Что изменилось в ошибках API

В предыдущем JSON вопрос об обязательности `result` отсутствовал. Его можно было увидеть только при чтении HTML/PDF. В новом отчёте владелец получает вопрос прямо в замечании **D-15**: «Каков статус каждого из полей `result` и `enabled` (обязательно, необязательно или исключено) отдельно для HTTP 400 при неверных параметрах, HTTP 401 без авторизации, HTTP 404 для чужой или отсутствующей карты и HTTP 500 при внутренней ошибке?» В образцах HTTP 400, 401, 404 и 500 показан только `message`. Число 404 указано непосредственно перед соответствующим JSON внутри раздела 403. Это основание спросить о контракте. [Прежняя сверка](https://github.com/gojosatorukz/bcc-requirements-reviewer/blob/987e99a150942d3fd16df62f033b41630d56a0f2/eval/official-coverage/release.md) · [Текущая карточка](../runs/bcc-release/review.html#D-15)

## Вопросы и реплики дословно

**Первое сохранение.** Доступно ли «Сохранить» при первом открытии с выключенным уведомлением и пустым порогом и, если доступно, каким запросом с cardId и enabled=0 передать отсутствие порога? [Сценарий и цитаты](../runs/bcc-release/review.html#qa-scenario-1)

**Первый ответ владельца по месяцу покупки.** Для покупок на стыке месяцев завели отдельный счётчик «Переходящие». Это точно.

**Довопрос агента.** На сколько изменится каждый из трёх счётчиков (январь, февраль и «Переходящие») сразу после проведения 1 февраля покупки на 4 000 ₸ от 31 января?

**Уточнение владельца.** Когда месяц покупки и проведения по Алматы различается, после проведения вся сумма идёт только в «Переходящие». Январь и февраль по этой покупке остаются без изменений. Если оба события в одном месяце, вся сумма идёт только в обычный счётчик этого месяца. В «Переходящие» в этом случае ноль. [Машиночитаемый диалог](../runs/bcc-release/owner/dialogue.json)
