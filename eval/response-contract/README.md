# Какие поля может читать клиент после ошибки

В таблице API службы квитанций для `ticketRef` указывается назначение. Ответ 202 содержит этот ключ, а пример 503 содержит только `message`. Службе поддержки нужно знать, какой идентификатор запросить у человека, обратившегося после отказа архива. В этом эксперименте оба агента получали исходное ТЗ целиком. Новый сводный проход дополнительно получает ключи каждого JSON-объекта с номерами строк и разделом. Обязательность поля устанавливается только при наличии основания в тексте контракта. Паспорт каждого файла содержит версию кода, SHA-256 входа и время обращений. Эти три длительности относятся к отдельным запускам и не доказывают ускорение. Сохранённое поле `example_shapes` повторно вычисляется по исходным строкам при загрузке. Для объектов выводятся верхнеуровневые ключи, поэтому вложенные структуры по-прежнему требуют анализа реестра и документа.

## Проверка на документе BCC

На официальном входе агент прочитал шесть JSON-примеров. По двум примерам под 200 и четырём телам ошибок замечание D-12 адресует владельцу вопрос, при каких исходах гарантированы `result`, `amount`, `enabled` и `message`, включая возврат прежней настройки. В обосновании прямо отмечено, что отсутствие ключа в отдельном примере не устанавливает запрет в контракте. Дополнительно D-06 спрашивает, как клиент читает настройку до первого сохранения. Отдельный сценарий сохранения выключенного уведомления с ещё незаданной суммой этим полностью не покрывается.

Этот эксперимент с версией 6ba8863 также выявил дефект исполнения. Для D-06 гипотеза о чтении дала неподтверждённую числовую пару 30 000 / 50 000 ₸. В следующей версии у технических гипотез до построения программы отдельно проверяются область применения и предписанные исходы обеих сторон.
