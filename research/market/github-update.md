## Что проверить в своём агенте

**Регрессия порядка и бюджета модели.** Один и тот же фиксированный набор корректных ответов возвращается в предсказуемо разном порядке. При одном и четырёх слотах должны совпасть требования, ссылки, идентификаторы вопросов, приоритеты и ответственные решения. Отдельный счётчик должен показывать фактическое перекрытие при четырёх и отсутствие превышения заданного числа слотов. Из сравнения исключаем время и метаданные расписания. Такой тест выявляет ошибку планировщика, даже если две живые модели сформулировали бы разные вопросы. [Тест sau.ai](https://github.com/ruslan-berkin/sau.ai-mnuxbcc/blob/fbda3677f493ffef03cdca6c28e76c396ca50256/tests/test_parallel.py#L73)

**Изменение ровно одного правила.** В редакции без бизнес-изменений при перефразировании основания вопрос остаётся, а явная гарантия снимает свой вопрос. Полезный отрицательный контроль — независимое соседнее правило, которое перефразирование не затрагивает. В нашем бенчмарке планетария это POST 409, POST 503 и одноимённое поле соседнего GET 409. [Разметка преобразований](https://github.com/dol40n/requirements-validator/blob/65d30282349ec5dc7074575735a79e3d1181b1be/eval/metamorph.json) · [Проверки вопросов владельцу](https://github.com/dol40n/requirements-validator/blob/65d30282349ec5dc7074575735a79e3d1181b1be/tests/test_owner_questions.py) · [Наш независимый протокол](../../eval/field-obligations/protocol.md)

## Внешние инструменты API

В учебном примере **Specmatic** контрактные тесты сопоставлены с маршрутами реализации. Это разделяет реально достигнутые и исключительно документированные операции. Для статического ревью стоит раздельно показывать «правило следует из текста», «тело встречается в примере» и «поведение проверено на живом сервисе». В нашем хакатоне доступен документ, а последняя величина для банковского API неизвестна. Корневой LICENSE репозитория labs — MIT. Это не свидетельство об условиях любого отдельного продукта Specmatic.
