# Повторяемость приоритетов

В этом испытании агент трижды читает один и тот же файл с нуля. Цель — проверить, получит ли конкретный дефект тот же приоритет, если он будет найден заново. Отдельно учитывается, сколько раз агент обнаружил каждый дефект.

Первый документ — [официальное ТЗ BCC-HUB на фиксированном коммите](https://github.com/BCC-HUB/ai-requirements-validator-task/blob/928c1aa364265426105b69ba7a3444eac11b22db/docs/requirements.md). Второй — [новая спецификация о высвобождении резерва продавца](merchant-reserve.md). Ожидаемые результаты для обоих входов зафиксированы в [протоколе до прогонов](controls.md). Согласованная строка приёмки на 17 000 ₸ служит отрицательным контролем.

## Результат

| Вход | Находок в запусках 1 / 2 / 3 | Приоритет в каждом запуске | Заранее заданные проверки |
|---|---|---|---|
| Официальное ТЗ | 16 / 16 / 16 | 2 критических, 13 существенных, 1 редакционное | 12 совпадений из 12 |
| Резерв продавца | 3 / 3 / 3 | 1 критическое, 1 существенное, 1 редакционное | 9 совпадений из 9 |

Каждая из 19 сопоставленных проблем появилась во всех трёх прогонах своего документа с одним приоритетом. В официальном ТЗ конфликт месяца учёта покупки и противоречащие правила о втором push каждый раз получили критический приоритет. Запись через GET получила существенный приоритет в обоих документах. В новом ТЗ агент трижды выделил расхождение READY/HELD при равенстве сумм и сохранил редакционный приоритет у расхождения в фамилии. Согласованную выплату на 17 000 ₸ ни один из трёх прогонов не назвал конфликтом.

Все 57 итоговых записей вошли в ручное сопоставление. Номера внутри уровня приоритета и разбиение текста на отдельные требования могут различаться. Например, замечание о GET в официальном ТЗ имеет номера D-10, D-09, D-09, а реестр нового ТЗ содержит 24, 24 и 26 пунктов. Эксперимент измеряет повторяемость на двух документах. Полноту по всем возможным дефектам реального банковского ТЗ он не оценивает.

| Документ | Первый прогон | Второй прогон | Третий прогон |
|---|---|---|---|
| Официальный | [291 с](../../runs/bcc-priority/review.json) | [640 с](runs/official-2.json) | [275 с](runs/official-3.json) |
| Резерв продавца | [141 с](runs/reserve-1.json) | [139 с](runs/reserve-2.json) | [144 с](runs/reserve-3.json) |

В шести паспортах указаны модель `gpt-6.2-astra`, единый движок `ab5bbb5329f4…` и шкала `impact-v1`. Во время испытания до трёх полных запусков делили доступ к провайдеру. Измерения времени включают ожидание его ответов.

## Методика

Каждый запуск заново выполняет разбор блоков, поиск поведенческих конфликтов и итоговое ревью документа. Команды запускаются без `--checkpoint-dir`. Номера замечаний действуют только внутри одного отчёта. В карте сопоставления замечания объединены по решению, которое должен принять аналитик, с учётом цитат и условия срабатывания. При сравнении учитываются также находки сверх заранее заданного списка.

Для повтора полной проверки сохраните официальный файл в текущем каталоге под именем `requirements.md`. Каждая из команд ниже вызывает модель трижды.

```sh
for n in 1 2 3; do python3 -m reviewer requirements.md "output/official-$n.json" --workers 4; done
for n in 1 2 3; do python3 -m reviewer eval/priority/merchant-reserve.md "output/reserve-$n.json" --workers 4; done
```

Для проверки опубликованных результатов из корня репозитория выполните `python3 -m eval.priority.audit`. Команда валидирует цитаты и приоритеты, сравнивает контрольные суммы входов и движка, проверяет отсутствие восстановленных стадий и сверяет каждое замечание с [ручной картой сопоставления](matches.json). Повторная проверка сохранённых данных выполняется без вызова модели.
