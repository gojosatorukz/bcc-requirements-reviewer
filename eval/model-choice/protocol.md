# Сравнение GPT-6.2 Sol и GPT-6.2 Astra

Протокол записан до запуска Sol. Сравниваем одно полное ревью каждой моделью на каждом из трёх входов. Эталон Astra — три уже сохранённых отчёта `full-*.json` из [предыдущего эксперимента](../blind-clearing/README.md). Четыре целевых дефекта и отрицательные контроли зафиксированы в [протоколе отмены](../blind-clearing/protocol.md) и [матрице BCC](../../docs/case-matrix.md).

## Условия

- Дерево движка `b3cbebdae0a4` без изменений, запуск с `--workers 4`, Codex CLI и одна и та же команда полного ревью с заменой `--model`. Используем свежие запуски без восстановления контрольных точек. Кеш провайдера может вернуть совпадающие токены и фиксируется отдельно.
- Входы — официальный Markdown BCC на [коммите 928c1aa](https://github.com/BCC-HUB/ai-requirements-validator-task/blob/928c1aa364265426105b69ba7a3444eac11b22db/docs/requirements.md), [исходная отмена](../blind-clearing/clearing.md), [исправленная отмена](../blind-clearing/clearing-fixed.md). Проверяем равенство SHA-256 в паспортах обеих моделей. Протокол и эталонные ответы в промпты не передаются.
- По одному независимому запуску на вход для каждой модели. Сохраняем первый завершившийся отчёт. При отказе показываем также сам отказ и его причину. Внутренние повторные вызовы при валидации считаем попытками, они входят во время и токены.

## Что считаем

| Критерий | Проверка |
| --- | --- |
| Покрытие четырёх дефектов | BCC: месяц учёта (38 и 64) и повторный push (39 и 40), оба критические. Исходная отмена: исход QUEUED/CANCELLED ровно в 16:00:00 без блокировки (7 и 15), критический. Невалидный JSON успешного ответа (25–29), нарушение контракта. Засчитываем по смыслу сценария, конкурирующим исходам и фактическим цитатам. |
| Отрицательные контроли | Отмена в 15:59:59 и 16:00:01, отказ при ручной блокировке. Оба случая согласованы в обеих версиях. В исправленной версии не должно быть прежней ошибки на 16:00:00 или прежней ошибки JSON. |
| Проверяемость и артефакт | Сверяем все ссылки line/quote по исходнику, результаты детерминированной проверки JSON, состав реестра и отдельные выводы о готовности. Число пунктов само по себе не является оценкой полноты. |
| Дополнительные замечания | Отмечаем подтверждённые дубли, неподтверждённые утверждения и важные различия приоритета или категории. Неизвестные владельческие решения не считаем ложными дефектами без явного основания. |
| Ресурсы | Сравниваем стеновое время, входные и выходные токены, вход из кеша и число принятых/отклонённых вызовов. Фактическую цену не рассчитываем без данных биллинга. |

На этих входах Sol будет кандидатом для дополнительной проверки, если сохранит все четыре дефекта с проверяемыми цитатами, пройдёт отрицательные контроли и JSON-проверку и покажет преимущество по наблюдаемым ресурсам. Любой пропуск или ложное закрытие отмечаем независимо от скорости. Одного запуска на вход недостаточно, чтобы менять модель по умолчанию или делать вывод о надёжности на других документах.
