# Может ли агент показать точные имена статусов

Это новый синтетический договор GET о банковской выписке. Имя поля и пять допустимых строк заданы во входе. У статуса нет порядка или числового значения. Эталон записан до первого вызова модели. Автор не участвует в разработке интерпретатора.

| Наблюдение в ответе GET | Правило публикации | Мобильная приёмка |
| --- | --- | --- |
| После регистрации, до первой попытки | QUEUED | QUEUED |
| После первой попытки, подпись временно недоступна | AWAITING_SIGNATURE | MANUAL_REVIEW |
| Та же последовательность, выписка подписана | READY | READY |
| Та же последовательность, сертификат отклонён | REJECTED | REJECTED |

В исходной редакции ожидается замечание о строке 13 и последней строке таблицы. После изменения одной строки обе стороны требуют AWAITING_SIGNATURE. Факт расхождения и полноту вычисленного ответа оцениваем отдельно.

1. Полное вычисление возвращает конкретные исходные имена обоих статусов. Нормально использовать внутренние коды, если отображение в строки однозначно и все заявленные результаты согласуются с таблицей. Человеку в интерфейсе должно быть понятно, какой статус получит клиент по каждой трактовке.
2. Допустимая частичная проекция проверяет явно названный вопрос, например «вернулся ли MANUAL_REVIEW?». Соседние варианты READY и REJECTED оба дают «нет». Такая проекция может доказать расхождение, но не позволяет восстановить полный ответ GET. Само по себе число 0 не означает AWAITING_SIGNATURE.
3. Если язык вычислений не позволяет честно выразить поведение, агент может показать источник, точный вопрос владельцу и ограничение исполнения. Безымянные коды, произвольная шкала, подсчёт вызовов оператора или денежных сумм здесь не подтверждают заявленное расхождение.

Для повторной проверки на сохранённой программе будем менять исход первой попытки и проверять оба независимых согласованных исхода, если предложенная программой форма входа это допускает. Для программы, ограниченной одним из контролей, явно отмечаем это ограничение. Для согласованной копии содержательный конфликт об этом поле исчезает.

## Первый результат

На `b98a4f3` обычное полное ревью исходника заняло 118,76 с и потребовало четыре свежих вызова Astra. Агент нашёл ровно один критический конфликт и задал владельцу контракта точный вопрос, что вернёт первый GET после временной недоступности до следующей попытки, AWAITING_SIGNATURE или MANUAL_REVIEW. Привязка верна для обеих строк, 13 и 22. Генератор указал `unsupported` и объяснил, что целочисленная модель не выражает строковый ответ. Исходные значения сохранены в замечании. [Первый полный отчёт](../runs/before-named-state.json)

На исправленной редакции за 104,22 с и три свежих вызова агент оставил один открытый вопрос о достижимости MANUAL_REVIEW в текущей поставке. Этот статус всё ещё присутствует в общем справочнике, хотя ни один из описанных результатов первой попытки больше не приводит к нему. [Первый согласованный полный отчёт](../runs/before-named-state-aligned.json)

## Результат после добавления именованных типов

Обычный полный запуск `d96338e` самостоятельно выделил два словаря, пять точных значений GET и три разных ответа сервиса подписи. Обе трактовки начинают в QUEUED. На исходном документе за 5 новых вызовов и 151,61 с модель построила программу и прошла независимую смысловую проверку. Офлайн-повтор подтвердил все три строки таблицы выше, включая REJECTED при отклонённом сертификате. При проектировании агент выбрал для контрольного примера другую ветку, успешную подпись. Согласованный документ потребовал 3 новых вызова и 103,64 с. В нём ноль итоговых замечаний и программ. [Полное ревью с программой](../runs/named-state.json) · [Полное ревью согласованной редакции](../runs/named-state-aligned.json)

Отдельно с тем же самым ранее найденным замечанием проверили только генератор программы и смыслового аудитора. За 2 вызова и 43,79 с эти стадии преобразовали прежний отказ в исполняемую программу с теми же правильными результатами для всех трёх входов. Дополнение хранит SHA-256 исходного отчёта. [Дополнение к прежнему замечанию](../runs/named-state-upgrade.json)

Из корня проекта обе команды заново исполняют сохранённый код с каждым из трёх ответов сервиса.

```sh
python3 -m eval.executable.named_state_probes
python3 -m eval.executable.named_state_probes --upgrade
```

## Передача отчёта другому аналитику

Аналитик открыл скачанный JSON через форму импорта в новом рабочем месте. Приложение пересчитало сохранённую трассу и вернуло исходный файл с тем же SHA-256. В браузере смена результата подписи на отклонённый сертификат дала `REJECTED` для обеих трактовок. Повторная загрузка того же файла открыла уже созданный разбор.

В новом ответе владелец потребовал показывать `AWAITING_SIGNATURE` **от регистрации до следующей попытки**, если сервис подписи временно недоступен. Агент принял формулировку за один вызов (17,07 с). В исправленной редакции первый GET после сбоя уже правильно возвращает `AWAITING_SIGNATURE`. Но до первой попытки строка 8 всё ещё предписывает показывать `QUEUED`. Адресная перепроверка за два модельных вызова (31,42 с) пометила первоначальный конфликт как устранённый и оставила замечание открытым из-за более широкого условия владельца.
